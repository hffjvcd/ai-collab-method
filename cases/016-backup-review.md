# 案例：一次备份工具链的质量审查

> 脱敏说明：本案例只保留方法论形状。日期、主机、路径、任务名、文件数量均已移除或改写为通用说法。

## 背景

一个备份工具链由四个脚本组成：同步并提交、恢复、看门狗、计划任务注册。
审查目标不是「它能不能跑」，而是「它在什么情况下会悄悄跑错」。
审查方被要求全程只读，只核验、不修改。

## 审查的四个维度

1. **正确性** —— 每个设计判断是否有证据支撑。
2. **完整性** —— 新旧两条链逐项对照，而不是只看新链自己是否自洽。
3. **副作用** —— 失败路径、并发、文件系统边界。
4. **一致性** —— 同一份清单在三个地方是否逐字一致。

## 真正的发现：三个 bug

### B1 滞留提交永不重推

推送只在「本次运行产生了提交」时执行。若某次门禁挡住或推送失败，本地提交会滞留；
下一次运行若没有文件变化，就走进「无需提交」分支，推送分支根本不会进入。
结果：滞留提交要等到某个文件恰好变化才会被推走。

**修正**：把推送条件改为「工作区干净 + 上游与 HEAD 之间有差异」，
与本次是否提交解耦。

### B2 大文件门禁跑在提交之后

先 `git add -A`、再提交、最后才检查单文件大小。此时超大文件已经进入本地历史。
git 历史不能撤回：这个对象会永久留在仓库里，每次克隆都背着它，
而且不会因为「下次门禁通过」而消失。

**修正**：在 `git add` 之前，用 `git ls-files -o -m --exclude-standard` 预检
即将入库的文件；提交后再用 `git ls-files -s` 做一次兜底。

### B3 把网络问题误报成备份故障

推送被挡时整体状态被置为失败，而「最后成功时间」只在整体成功时推进。
于是本地备份每次都对，看门狗却连续报「两次失败」，36 小时后还会报「从未成功」。

**修正**：状态文件拆成两个字段 —— `local_status`（备份本身成没成）与
`push`（快照出没出机器）。退出码只看前者。

## 覆盖清单对照：不能只看新链是否自洽

审查发现新旧两条链的定位不同：旧链是「数据备份」，新链是「配置档案」。
逐项对照的结果是「重叠 4 / 收窄 4 / 缺失 6」。这意味着：

- 两者不是替代关系，并行期必须真的并行；
- 停掉旧任务之前，必须为缺失项给出保留方案，否则丢的是数据不是配置。

最容易被漏掉的一条：旧链上还有一个独立的健康检查任务，它读的是旧链的日志。
一旦停掉旧链，它会**每天**误报「备份过期」，而新看门狗对此一无所知。
这个陷阱只有把「谁还会读旧链的产物」问一遍才会浮出来。

## 方法要点

- 审查提示词用红队式：「请尽量找出漏洞、被忽略的假设、副作用」，而不是「评估是否可行」。
- 每个结论必须能指回文件与行号；指不回去的就写「未能验证」。
- 只做静态检查与 dry-run 的，明确标注「未做非 dry-run 实测」，
  不把「没测」写成「没问题」。
