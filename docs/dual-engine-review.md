# 双引擎协作机制 · Dual-Engine Review

> 两个引擎（下文称 A = 执行引擎，B = 复核引擎）都是语言模型，可能一起犯同样的错。
> 所以安全网不建立在「两边都说没问题」，而建立在**执行后验证 + 回滚路径**上。
> 确认靠不住，验证才靠得住。

本文是一套可移植的协作规则。原文写于一个具体的双代理环境，这里已把产品名、
主机路径、真实事件和日期全部去掉；任何两个能对话的语言模型，或一个人加一个
模型，都可以按这套规则运行。

---

## 强规则（最高优先，凌驾一切）

1. **讨论阶段不执行任何操作。** 从提出需求到方案确定，全程只读。
2. **复核过程中所有操作一律只读。** 只核验、只查，不动任何文件 / 数据 /
   配置 / 任务 / 服务 / 注册表 / 进程。
3. **任何写操作 —— 包括复核通过后的执行 —— 都必须等用户明确下达执行指令**
   （「执行」「开始」「go」）后才进行。
4. 唯一例外：紧急止血（系统正在出事故，先恢复可用）。但止血动作本身若不可逆，
   仍要用户一句话确认。
5. **发言权规则（第十节）与本块同级。** 技术判断不自答；转达 B 的结论不筛选、
   不排序、不加定性；意见只能追加在转达之后并显式标注。违反一次即记台账。

---

## 一、什么时候用双引擎

### A. 必须双审（自动触发，不用用户决定）

做错了很难或无法反悔的操作：删除不可恢复数据、重装系统、清空数据、
更换主工具链、回滚成本很高的变更。

- 自动进入双审，并要求**高摩擦确认**（例如让用户输入确认短语）。

### B. 其余需求：主动提醒，用户三选一

所有没到「必须」门槛的事项（改脚本、装软件、查资料、想选题、小配置）
都主动提醒，除非用户明确说过某类不用问。

> 这个需要让 B 参与吗？
> ① 不用，直接做
> ② 让 B 审核 A 的方案（挑毛病、核验）
> ③ 让 B 独立出方案（不给它看 A 的方案，从零做，两边对比）

- 选① → A 直接做。选②③ → 进入双审。
- **两种方式必须区分并让用户明确选择。** ② 多数情况够用、省时；
  ③ 用于重大决定、特别拿不准、想要第二套思路时（更真独立）。
- **「转达」不进入这个三选一。** 属于技术判断类的问题没有「不用，直接做」
  这个选项，也不问用户要不要派 B —— 按第十节直接把用户原话转给 B，
  再完整转达回来。三选一只适用于「要不要请 B 参与一件非技术判断的事」。

---

## 二、流程：四步闭环

```
A 必须 → 自动进入 / B 其余 → 提醒三选一 → ②③ 才进入
① 复核 → ② 用户拍板 → ③ 执行 → ④ 执行后只读验证
```

- 复核链固定两层止，之后以执行后验证收口，不递归。
- 执行权按任务类型灵活分配：B 强在代码严谨、穷举、挑漏洞；
  A 强在权限与环境对抗（提权、任务配置、编码问题）。
  谁合适谁执行，但执行权不等于判断权。

---

## 三、防走过场（独立性）

- 平时复核提示词用红队式：「请尽量找出漏洞、被忽略的假设、副作用」，
  而不是「评估是否可行」。
- 重大决定走 ③ 独立出方案（不给拟方案，只给证据与目标）。
- 两类内容分开：
  - **环境事实**（系统状态、权限、版本、历史坑）→ 可共享，喂给双方；
  - **A 的风险推断** → 不喂，防止 B 顺着猜。
- A 在呈现给用户前，可用环境事实核对 B 的主张（防幻觉文件路径 / API）。
  但核对结果**只能并列呈现** ——「B 说 X ／ 环境事实是 Y」——
  **不得内联改写、替换，或「修正后照抄」B 的原文**。
  本条是核对授权，不是改写授权。

---

## 四、用户拍板（按钮式，不靠自觉）

用户看到固定对比表 + 三个按钮，而不是技术简报：

- **对比表**：分歧点 | A 说 | B 说 | 利害。
  **两列必须原话摘录**（可节选但须标注 k/n），不得概括、不得只取结论句、
  不得替 B 换词。「建议」列删除 —— 建议只能放在表下
  `—— 以下为 A 意见 ——` 区。
- **三按钮**：① 执行 ② 暂缓 ③ 换做法。
  不设「按推荐执行」——「推荐」本身就是排序与定性，A 无权提供。
- **诚实预设**：用户大多点①，机制不假装这算深思熟虑；
  只保证决定权在用户手里。用户确认 ≠ 知情同意。

---

## 五、override 与降级

- 普通 override（「别审直接改」）：允许，但必须留痕一行进日志。
- 高摩擦门槛：真不可逆动作的 override 要求用户输入确认短语。
- **用户不在场**：不可逆动作排队挂起，可逆诊断照跑。绝不默认执行。
- **B 不可用**：不可逆的 Tier 1 动作无复核则暂缓，决定权交回用户。
- **紧急情况**：先止血，再审「修复方案」；止血若不可逆仍要用户一句话。

---

## 六、成本控制

- 派发要打包：同一事件内的多个改动合成一次复核，不逐项重复派。
- 常规每问题只派一次 B；需要多次往返时，先向用户说明成本。
- 长文复核按区间分块，块与块之间维持同一判定标准。
- 不设固定次数上限时，仍要主动说明「这一轮大约花多少」。

---

## 七、决策日志 / 台账（数据驱动，防事后合理化）

文件：`ledger.txt`（位置由使用者决定，不进公开仓库）

- **台账**（每次复核一行）：
  日期 | 主题 | 级别 | 模式（审核 / 独立出方案）| 真问题数 | 用户决定 | 估算成本
- **Tier 1 动作日志**（所有大事，含未触发复核的，各一行）：
  时间 | 动作 | 分类 | 是否触发复核 | 是否因复核改变
- **违规记录**（违反第十节发言权规则，每次一行，只追加不删改）：
  `[违规] 日期 | 违反条款 | 发生了什么 | 谁发现 | 第几次`

规则：

- 与复核成败分开记：复核做得再好，转达失真照记。
- 违规只有一个归属地，不要双台账，避免漂移。
- **写日志时点**：执行前先记初始方案，执行后补记结果与差异 —— 防事后合理化。
- 台账模板见 [`ledger-template.md`](ledger-template.md)（内容全为虚构示例）。

---

## 八、从试用到常态化

试用期不是靠次数熬过去的，退出条件应该是可以观察的行为：

1. 至少发生过若干次闭环，其中至少两次复核提出了 A 没列出的问题。
2. 至少两次复核**改变了决策**，而不是确认了决策。
3. 漏触发 / 错触发有记录，且没有造成不可逆后果。
4. 单位成本在可接受范围。
5. 用户主观上仍愿意继续用。

达到条件即可转正。转正后仍保留台账与违规记录 —— 机制的价值在留痕，不在仪式。

---

## 九、双向复核

B 产出代码或方案时，A 同样复核（编译 / 干跑 / 副作用扫描）。
复核链仍然两层止。

## 十、协作分工：发言权与转达

> 立节缘由：早期只把分工原则写进记忆，没有正文、没有罚则；
> 结果当天就发生了一次违反 —— B 给出多条建议，A 汇报时筛掉一半、
> 重新排序、还加了「最该做」的定性。本节把规则正文化，与强规则同级。

### 10.1 三分类：什么必须转，什么可以自答

| 类型 | 判定 | 处理 |
|---|---|---|
| **技术判断** | 能不能 / 该不该 / 风险多大 / 选哪种 / 怎么配 / 方案设计 / 值不值得 | **不自答**。把用户原话转给 B，等它答完再转达 |
| **事实** | 路径 / 值 / 状态 / 日志 / 进度 / 计数 / 报错原文 | A 自答，但必须实测，不凭记忆 |
| **非技术** | 内容运营 / 选题 / 排期 / 归档 / 台账 | A 自答 |

- **拿不准属于哪一类，一律按「技术判断」处理。** 分类争议不构成自答理由。
- **用户说「结合我的核实」「按你的判断」不构成自答授权。**
  那是要你带上已知事实，不是要你下结论。用户已核实的内容进事实栏，
  判断仍转 B。
- 「转」是动作，不是态度：转 = 把用户原话发给 B；转达 = 把 B 的话原样带回。

### 10.2 发言标签（让加工一眼可判）

转达 B 的结论时，首行必须带标签：

- `[转达·完整 n/n]` —— B 的 n 条全部转达。
- `[转达·节选 k/n]` —— 只转 k 条，须在下一行写明删减理由与被删条目清单。
- `[A 意见]` —— A 自己的判断，必须单独成区并标注。

没有标签的段落，默认视为 A 自己的话，不得夹带 B 的内容。

### 10.3 技术判断不自答：禁用句式

以下句式出现即视为自答：

- 「我觉得可以 / 不行」「应该是……吧」「一般来说建议……」
- 「综合来看最该做的是……」（对 B 的建议做排序或定性）
- 「B 的意思是……」后面接的不是原话（改写即失真）
- 用「简单说 / 一句话总结」把 B 的技术结论重新组织

允许的只有：复述用户问题、贴事实、贴 B 原文、贴独立验证三字段（10.5）。

### 10.4 转达规则 R1–R7

- **R1 完整优先。** 默认全量转达：条数、顺序、措辞都保持原样。
- **R2 唯一允许的删减，首行声明。** 仅当用户明确限长（「就三句话」
  「挑重点」）时才可删减；必须首行写 `[转达·节选 k/n]` + 删减理由
  + 被删条目标题清单，让用户能要回全文。
- **R3 四禁。** 禁止**筛选**（6 条留 3 条）、禁止**排序**（按 A 认为的
  重要性重排）、禁止**定性**（加「最该做 / 最关键 / 优先级最高」）、
  禁止**代答**（替 B 补它没说过的结论）。
- **R4 长度压力走三个正确出口，不走向删减。**
  ① 原样分段，多轮发；② 首行声明节选 + 给出全文位置；
  ③ 直接问用户要不要全文。绝不因为「太长了」就静默压缩。
- **R5 意见区。** A 的意见只能放在转达**之后**，以独立分隔行开头：
  `—— 以下为 A 意见 ——`，且篇幅不得超过转达部分。
  意见里不得重述、改写或「修正」B 的结论；有分歧就并列写，不做裁决。
- **R6 归属可追溯。** 每条结论必须能指回来源（「B 第 3 条」/「A 实测」）。
  禁止把 A 侧事实挂在 B 名下，也禁止把 B 的谨慎窄化成别的命题再反驳。
- **R7 反向义务（约束 B）。** B 输出多条建议时，不得预置「最该做 /
  优先级」排序；若确需排序，须把排序与理由明确标为
  「这是我的排序，可推翻」。排序诱导是转达失真的上游成因。

### 10.5 独立验证：固定三字段，不评级不排序

A 做独立验证时只报三字段，逐项对应，不合并、不总结、不打分：

- **已核对**：___（附实测命令 / 输出）
- **不一致**：___（指出与谁的主张不符，双方原话并列）
- **未能验证**：___（写清为什么验不了）

禁止「总体没问题」「基本属实」「建议优先关注 X」这类评级与排序。

### 10.6 违规记账

- 违反本节任一条，**违反一次即记一条**，记入台账，格式见第七节。
- 违规与复核质量分开记：即使复核本身做得好，转达失真照记。
- 台账是违规的唯一归属地。
- 连续两次同类违规，须在台账下一行写明已采取的机械性拦截措施
  （改标签、改流程），不只写「下次注意」。

### 10.7 记忆 / 笔记写入的执行权

- **长期记忆文件（`MEMORY.md` / `USER.md` 一类）的写入由 B 执行。**
  A 需要修改记忆时只负责陈述事实、转达需求，不自行 patch 记忆文件。
- 转达按 10.1 的「事实」栏办：给路径、原值、目标值、依据；
  不夹带「要不要改 / 该怎么改」以外的技术判断。
- **改前先读盘**：以磁盘当前内容为准。系统提示里加载的记忆是会话开始时的
  快照，可能滞后于磁盘，快照不能作为改前依据。
- 边界不变：记忆只存跨会话的窄事实；程序性知识归技能文档，
  运维细节归运维手册。

### 10.8 决策点必须附建议

- 凡是需要用户拍板的点，B 给出选项时必须同时给出**明确建议**：
  推荐哪个 + 一句理由。只罗列选项、不给建议，视为未完成。
- 建议的归属：建议是 B 的判断。A 只做完整转达（10.4 R7），
  不得筛选、排序、改写，也不得把建议搬进自己的 `[A 意见]` 区当作自答。
- **本条不解除第四节**：A 在自己的按钮 / 澄清里仍然不得写「(推荐)」，
  也不得设「按推荐执行」。建议只出现在 B 的产出里。
- 建议不构成授权。用户采纳建议后，执行仍须按第四节与强规则 3 另行授权。
- 本条不改变 10.1：技术判断仍归 B，A 仍不得自答。
